# Персональные данные и законодательство РФ (152-ФЗ) для CRM и MCP

Этот документ — **операционный чеклист** для церкви-оператора CRM. Он не заменяет консультацию юриста, но перечисляет обязательные меры, без которых нельзя считать обработку ПДн «закрытой».

Нормативная база: Федеральный закон № 152-ФЗ «О персональных данных», подзаконные акты Роскомнадзора, требования к локализации (ч. 5 ст. 18), уведомление об инцидентах, трансграничная передача (ст. 12).

## 1. Кто оператор

- Юридическое лицо / религиозная организация, от имени которой ведётся CRM, — **оператор ПДн**.
- Зарегистрируйте (уведомите) обработку в Роскомнадзоре, если нет оснований для исключения.
- Назначьте ответственного за организацию обработки ПДн.
- Утвердите политику обработки ПДн и опубликуйте её (сайт церкви / CRM).

## 2. Правовые основания

Допустимые основания в контексте домашних групп:

1. **Согласие субъекта** — публичная заявка в ДГ (`personal_data_consent_text`, флаг `consent_given`).
2. **Исполнение устава / пастырская деятельность** в рамках законных интересов / специальных категорий — только после юридической квалификации (религиозные данные часто относятся к специальным категориям ПДн — ст. 10).
3. **Трудовые / договорные** отношения для сотрудников — отдельно.

В интерфейсе уже есть настраиваемый текст согласия (`/church-settings`). Адаптируйте его под полное наименование оператора, адрес, цели, срок, способы отзыва.

## 3. Локализация баз данных (ч. 5 ст. 18)

При сборе ПДн граждан РФ запись **первично** должна осуществляться в базу на территории РФ.

Практически:

- Хостинг MySQL и файлов CRM — в РФ (Timeweb и аналоги уже в контуре).
- Резервные копии — тоже с учётом локализации (или шифрование + правовой режим хранения).
- CDN/логи за рубежом не должны становиться **первичной** записью ПДн.

## 4. Цели, минимизация, сроки

| Цель | Какие данные | Срок |
|------|--------------|------|
| Участие в ДГ, забота, посещаемость | ФИО, контакты, даты посещений | пока человек в общине + срок хранения из политики |
| Аналитика здоровья групп | агрегаты + идентификаторы в CRM | по политике |
| MCP / ИИ-агенты | только необходимые поля ответа инструмента | не дольше, чем нужно агенту; не логировать лишнее у вендора |

В MCP уже:

- отдача урезанных карточек (`care_public_person_row`);
- **запрет** выдачи `sensitive_notes_encrypted`;
- scopes + RBAC;
- audit каждого tool call.

Задайте `retention_until` / регламент удаления; используйте `/privacy` и `data_deletion_requests`.

## 5. Трансграничная передача (самое важное для MCP)

Подключение Cursor / ChatGPT / облачных LLM к `/mcp` означает, что ФИО, телефоны, факты посещений могут уйти на серверы **вне РФ**.

Чтобы соблюсти 152-ФЗ:

1. **По умолчанию** используйте MCP только с **локальными** моделями / on-prem агентами, либо с вендорами, у которых есть законный механизм трансграничной передачи.
2. Получите **отдельное согласие** субъектов на трансграничную передачу (или иное основание ст. 12) **до** подключения облачного агента к production.
3. Заключите договор / DPA с обработчиком (AI-провайдер), зафиксируйте цели, меры защиты, запрет обучения модели на ваших данных где это возможно.
4. Оцените, является ли передача в «ненадёжные» юрисдикции — тогда нужны дополнительные условия ст. 12.
5. Минимизируйте scopes ключа (`read` без `people`/`roles`, если агенту достаточно аналитики).
6. Не используйте production-ключ в публичных демо и чужих машинах.

Без пунктов 1–3 подключение облачного MCP к боевой базе с ПДн граждан РФ — **высокий юридический риск**.

## 6. Права субъекта

Обеспечьте процедуры:

- доступ к своим данным;
- уточнение (профиль / карточка / MCP `update_profile` / `update_person`);
- отзыв согласия;
- удаление / обезличивание (`/privacy`, soft-delete в `people.deleted_at`);
- обжалование.

Срок ответа на запрос субъекта — по политике оператора (обычно до 30 дней, лучше быстрее).

## 7. Защита и меры

Уже в продукте / обязательно в эксплуатации:

- [x] HTTPS, HttpOnly session cookie, CSRF для браузера
- [x] Хеши паролей, опциональная 2FA
- [x] Шифрование чувствительных заметок
- [x] RBAC + field permissions + scoped SQL
- [x] Audit log ключевых действий и MCP
- [x] API-ключи только как SHA-256 hash, показ токена один раз, revoke, expiry, лимит на пользователя
- [x] Rate limit на `/mcp`
- [ ] Регламент инцидентов: уведомление Роскомнадзора **в течение 24 часов** с момента обнаружения утечки
- [ ] Внешний секрет `security.encryption_key`, ротация
- [ ] Off-site backup + тест восстановления
- [ ] Журнал выдачи API-ключей служителям (кто, зачем, до когда)

## 8. Специальные категории и служение

Данные о вере, покаянии, крещении, молитвенных нуждах — потенциально **специальные категории**. Обрабатывайте их только при наличии законного основания и усиленных мер. В групповые бот-каналы уходит минимум фактов без персональных деталей (уже заложено в ботах).

## 9. Чеклист перед production MCP

1. Политика ПДн и текст согласия утверждены советом / юристом.
2. Уведомление Роскомнадзора актуально.
3. БД и бэкапы в РФ.
4. Решено: только локальный агент **или** оформлена трансграничная передача.
5. Ключи выдаются лично, с минимальными scopes и сроком.
6. Ответственный умеет отозвать ключ и выполнить запрос на удаление.
7. Инцидент-плейбук подписан.

## 10. Что уже закрыто кодом в wolhg

- Согласие при публичной заявке
- Удаление/обезличивание по запросу
- Audit
- Минимизация MCP-ответов
- Разделение прав по ролям и scopes

Что **нельзя** «закрыть кодом» — регистрация оператора, договоры с AI-провайдерами, согласие на трансграничную передачу, организационные регламенты. Это зона церкви-оператора.
